# תוכנית: סידור מסלול לשליח (Delvr v1)

סטטוס: טיוטה לאישור. נכתב 2026-10-20.
קלט: ספק `docs/specs/route-optimizer.md` (אושר), ספייק `docs/spikes/hebrew-dictation.md` (GO בתנאי), פירוק `docs/teardowns/spoke-route-planner.md`.

## 1. מצב קיים
אין עדיין קוד אפליקציה. יש רק את קוד הספייק ב-`spikes/hebrew-dictation/`: פרסר שעבר 50 מתוך 50 בדיקות, ועמוד ניסוי. את הפרסר מעבירים כמו שהוא לאפליקציה.

## 2. החלטות טכניות שבחרתי (אפשר לשנות לפני אישור)
| נושא | ברירת המחדל | למה |
|---|---|---|
| צד לקוח | Vite + React + TypeScript, כאפליקציית ווב שאפשר להתקין על הטלפון (PWA) | כך הוחלט בפלטפורמה. React עם TypeScript הוא הנפוץ ביותר, ויש לו הכי הרבה ספריות ומפות |
| שרת | פונקציה קטנה אחת (serverless) שמחזיקה את מפתח ה-Routes API | אסור לחשוף בדפדפן מפתח שאפשר לחייב דרכו כסף. הגיאוקודינג וההשלמה האוטומטית רצים בדפדפן, עם מפתח שמוגבל לדומיין שלנו |
| אירוח | Vercel, בחינם בהתחלה | נותן https, ובלי https המיקרופון לא עובד בטלפון. האתר והפונקציה נמצאים באותו מקום |
| זיהוי דיבור | Web Speech API של הדפדפן (`he-IL`) | הוכח בספייק: 20 מתוך 22 כתובות נכונות. בחינם, ובלי מפתח |
| שמירה | IndexedDB על המכשיר. אין משתמשים ואין שרת נתונים ב-v1 | המסלול וזיכרון הכתובות שייכים לשליח אחד. חשבונות אפשר להוסיף אחר כך בלי לשבור כלום |
| מספר עצירות | **עד 25 עצירות** ב-v1 | זו התקרה של קריאה אחת ל-`computeRoutes` עם `optimizeWaypointOrder`. מעל 25 יופיע הסבר. פתרון עם מטריצת זמנים ופותר משלנו יגיע בגרסה הבאה |

## 3. פרוסה ראשונה מקצה לקצה
הכי קטן שעובד באמת:
1. מזינים כתובת יציאה, או לוחצים "המיקום שלי".
2. מקריאים או מקלידים כתובות.
3. מאמתים כל כתובת מול Google. **מה ש-Google לא מזהה ככתובת מלאה עובר למסך תיקון** (כלל של המשתמש).
4. לוחצים "סדר", ומקבלים את הסדר האופטימלי עם זמן נסיעה, קילומטרים ושעת סיום.
5. מוצג "לפני ואחרי": הסדר שהוקרא מול הסדר החדש.
6. כל עצירה נפתחת ב-Waze, ומסמנים אותה "נמסר" או "נכשל".

## 5. ה-API של השרת
`POST /api/optimize`
- **קלט:** `{ origin, destination, stops: [{id, lat, lng, order: 'first'|'auto'|'last'}], departureTime }`. עד 25 עצירות.
- **מה הוא עושה:** קורא ל-`computeRoutes` עם `travelMode=DRIVE`, `routingPreference=TRAFFIC_AWARE`, `optimizeWaypointOrder=true`, `languageCode=he` ו-`regionCode=IL`.
- **עצירות ראשונות ואחרונות:** ה-API של Google לא יודע לנעול עצירה. לכן מסדרים רק את העצירות האוטומטיות, ואת הראשונות והאחרונות מצמידים בשרת לפני ואחרי.
- **פלט:** `{ order: [id...], legs: [{durationSec, distanceM}], totalDurationSec, totalDistanceM, finishAt }`.
- **כשלונות:** מעל 25 עצירות מחזיר 400 עם הסבר בעברית. כשגוגל נכשל, מחזיר 502, והמסלול נשאר בסדר שהוקרא עם הודעה. כשנגמרת המכסה, מחזיר 429.
- **הגנה:** מגבלת קצב לכל כתובת IP, ובדיקה שכל הקואורדינטות בתוך ישראל, כדי שאף אחד לא ישתמש בפונקציה על חשבוננו.
- **תקרה יומית בשרת:** הפונקציה מחזיקה מונה, ואחרי 150 סידורים ביום היא מחזירה 429. הסיבה: ב-Routes API ייתכן שאפשר להגביל רק לדקה ולא ליום, ו-5,000 בחודש בחינם הם בערך 166 ביום.

## 6. מצבי מסך
`draft` (מוסיפים כתובות) ← `verifying` ← `needs_fix` (יש כתובות לתיקון) ← `ready` ← `optimizing` ← `optimized` ← `driving`.
אחרי שהמסלול סודר, הוספת עצירה מחזירה אותו ל-`optimizing`, רק לעצירות שנשארו.

## 7. בדיקות
- **פרסר:** 50 המקרים מהספייק עוברים ל-Vitest, כולל שתי ההקלטות האמיתיות.
- **geocode ו-optimize:** בדיקות עם תשובות Google מוקלטות (לא אמיתיות): נמצא, חלקי, עיר אחרת, ראשון ואחרון, מעל 25.
- **בדיקה ידנית אחת מקצה לקצה בטלפון:** יציאה מיבנה, 10 כתובות בקול, תיקון, סידור, ופתיחה ב-Waze.

## 8. סיכונים
| סיכון | מה עושים |
|---|---|
| עלות Google | Routes עם תנועה וסידור מחויב בתעריף Pro. מגדירים מכסה יומית ב-Google Cloud כבר מהיום הראשון |
| מעל 25 עצירות | תקרה ב-v1. מטריצה ופותר בגרסה הבאה |
| זיהוי דיבור ב-iPhone | Safari תומך חלקית. ממליצים על Chrome. אם נצטרך, עוברים ל-Google Speech-to-Text דרך השרת |
| רעש ברכב | לא נבדק בספייק. נבדק בשלב 6 |

**חזרה לאחור:** כל שלב הוא commit נפרד. אין מסד נתונים בשרת, כך שאין מה לשחזר.
**מחוץ ל-v1:** חשבונות, משגר וצי, צילום רשימה, חלונות זמן, יותר מ-25 עצירות.
